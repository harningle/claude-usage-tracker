# Faithful Windows port of Claude Usage Tracker

## 1. Target, scope and evidence

Build a native Windows tray application using **C# / .NET 10 LTS and WPF**, preserving the upstream interface, workflows and useful behaviour. Deliver a personal-use build first, then prepare a public Windows release. Fidelity does not require reproducing upstream credential exposure, generating messages during ordinary polling, or macOS-specific implementation workarounds.

Use upstream commit [`588775e4540757443691fa1bcb33457315e05f86`](https://github.com/hamed-elfayome/Claude-Usage-Tracker/tree/588775e4540757443691fa1bcb33457315e05f86) as the fixed reference. Record deliberate baseline upgrades and each feature's implementation status, tests, live verification and Windows differences in `docs/parity.md`.

- Target Windows 11 x64, including PowerShell, Command Prompt and Git Bash with native Windows Claude Code. WSL, ARM64 and older Windows remain later compatibility work.
- Target PCs with one interactive Windows user. Shared and multi-user PCs (terminal servers, several people signed in to one machine) are out of scope (accepted 2026-10-01), so isolation between Windows users on one machine is not a design goal. Per-user DPAPI and ACL protections still apply because they are how secrets are stored.
- Include Claude and Codex profiles, guided setup, API costs, history, notifications, automation, terminal integration, passive activity HUD and redacted network diagnostics.
- Preserve upstream translations, licence notices and attribution. Omit telemetry and promotional prompts in both personal and public builds; document these intentional differences.
- Personal delivery includes a self-contained build, local registration needed by notifications/startup, manual upgrade and integration cleanup. Installer, signing and automatic updates belong to the later public-release milestone; they are not abandoned or claimed complete.
- No import of macOS Keychain or macOS app data. Existing native Windows CLI accounts can be linked through setup.
- The repository has the Milestone 0 scaffold and ported pure logic, plus Milestone 1 experiment harnesses in `spikes/`, but no application behaviour yet. .NET SDK **10.0.401** and native Claude Code **2.1.286** (auto-updated from 2.1.285) are installed; the latter resolves to `%USERPROFILE%\.local\bin\claude.exe`. Visual Studio Build Tools 2026 with the MSVC x64/x86 tools and Windows SDK 10.0.26100 is present, and NativeAOT publishing is verified ([Milestone 1 log](docs/milestone-1.md)).

### Evidence limits

The inspected source confirms browser clearance cookies, different active/background OAuth fetch paths, eight HTTP hooks, cookie-bearing statusline scripts and writes to the CLI's `oauthAccount`. Those facts are established; current endpoint availability and Windows authentication success are not.

Do not assume cookie replay works because both macOS clients use Apple networking, or fails merely because Windows clients use different stacks. Matching a user agent is necessary for a useful comparison, not proof of browser equivalence. [Cloudflare describes clearance as visitor/device-bound](https://developers.cloudflare.com/cloudflare-challenges/concepts/clearance/); live results must settle the Windows transport choice.

Without a Mac, visual references are SwiftUI source and upstream media, principally `.github/popover.png`, `settings.gif`, `icon.jpg` and `statusline.png`. Additional branding assets are not evidence of interactive behaviour. Record source/image-based fidelity separately from a future side-by-side Mac validation.

## 2. Architecture and deliberate adaptations

### Projects and test seams

Use **Core / App / Helper plus one Windows-targeted xUnit test project**. Core contains platform-independent usage models, calculations, parsers, statusline formatting and shared contracts. App contains WPF, providers, persistence and Windows integration. Helper references only Core and remains small enough for NativeAOT. Core and Helper target `net10.0`, so Core stays usable by the NativeAOT Helper. App and the test project target `net10.0-windows10.0.19041.0`: the Windows App SDK needs a versioned Windows target, and a test project can reference App only if its Windows target is at least as high.

Use lightweight MVVM. Keep interfaces for usage providers and credential storage. Use `HttpMessageHandler` and `TimeProvider` as HTTP/time test seams, temporary directories for file tests and concrete CLI/storage services until a demonstrated test need justifies another interface. Add a narrow browser-request adapter only if the authentication spike requires two transports; do not put WebView2 dependencies in Core or Helper.

Snapshots identify their profile, provider, data source and observation time. Preserve missing values rather than converting them to zero. Use `DateTimeOffset` for timestamps and decimal monetary values. Keep provider capabilities responsible for which settings and metrics are available.

### Browser authentication: a transport gate

In Milestone 1, sign in interactively using a profile-isolated WebView2 context. Compare the same read-only `/api/organizations` request through the browser and `HttpClient`, with the latter using the exact WebView2 user agent and correctly scoped `sessionKey`, `cf_clearance`, `__cf_bm` and `anthropic-device-id` cookies. Never log cookie values. Test an actual usage endpoint too: success on organisations alone does not prove all requests work.

Repeat after app restart, cookie renewal and a second isolated account; record runtime versions, HTTP status/content type, challenge indicators, latency and aggregate browser-process memory. Test Console authentication separately rather than extrapolating from claude.ai.

Decision rule:

- If replay repeatedly returns valid authenticated data, use a per-profile cookie container and `HttpClient` for that service. Synchronise renewed cookies and preserve domain/path/expiry rules; do not hard-code the upstream Safari user agent.
- If replay is challenged while the same browser request succeeds, use same-origin browser `fetch` through that profile's WebView2 context for that service. Forward only allowlisted operations and validated responses, not an arbitrary script/URL bridge. OAuth/provider endpoints that do not need browser state remain on `HttpClient`.
- If the browser itself cannot sign in or obtain data, mark that route unsupported pending investigation. Do not promise WebView2 is a guaranteed solution, bypass challenges, or classify a challenge as an expired account. Other proven authentication routes can proceed independently.

The WebView2 route has a measurable cost: separate user-data folders create independent browser process groups. Create contexts lazily, retain contexts needed for enabled background profiles and dispose disabled/removed profiles. Measure one and three profiles, both idle and polling, including startup latency; publish those measurements before accepting a lightweight-performance claim. [WebView2 process model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model)

Milestone 1 result (live account, 2026-10-01; details in [the Milestone 1 log](docs/milestone-1.md#3-browser-authentication-webview2)):
- **claude.ai uses same-origin WebView2 fetch**, by the decision rule above. Signed in with a personal (Pro) and a work (Team) account, browser fetch returned organisations and usage every time, including after an app restart. Every `HttpClient` replay was challenged: a valid `sessionKey` with the browser's clearance cookies, and either the WebView2 or upstream's user agent.
- **The Console uses `HttpClient`** with a per-profile cookie container against `platform.claude.com/api`, where its `sessionKey` is scoped. Replay there was not challenged.
- Keep an idle profile on a lightweight same-origin document such as `claude.ai/robots.txt`. That costs about 175-215 MB private per profile, against about 475-635 MB on the full claude.ai page.
- Background profiles' WebView2 hosts must stay realised (hidden, not detached), or initialisation stalls.
- On this machine a bare session key sent through `HttpClient` is challenged. Manual key entry therefore needs validating through the WebView2 route, or must lead to browser sign-in.
- A 30-minute polling soak returned 200 on 122 of 122 browser requests. Cloudflare re-issued `__cf_bm` every 15 minutes through the browser's own requests, and WebView2's cookie store absorbed it, so the route needs no cookie maintenance.
- Two profiles signed in to different accounts were isolated: different session cookies, different account IDs, no shared organisations. Clearing each after its browser processes exited removed its state.

Keep manual session-key entry as an advanced, capability-dependent setup path. Validate it through the selected transport; a bare key that is challenged must lead to browser sign-in without saving a successful configuration. Do not require users to paste Cloudflare cookies into chat or promise key-only setup works everywhere.

### CLI usage: no hidden generation

The baseline's active-profile OAuth path posts a one-token Haiku request to `/v1/messages`; its background-profile path still gets `/api/oauth/usage`. At the default 30-second interval the first path could make **2,880 generating requests per day**, and may start a session. Preserve neither this inconsistency nor its side effects accidentally.

Choose **read-only `/api/oauth/usage` for both active and background CLI profiles**, conditional on Milestone 1 live verification with valid CLI credentials. Use identical parsing and error behaviour; only the active profile may discover the system account. Do not infer current endpoint availability from the upstream comment declaring it disabled.

If the read-only route is unavailable, offer verified browser-session tracking or explicitly stale last-known usage. Never silently fall back to `/v1/messages`. A generating header probe is limited to an explicit diagnostic action with disclosure that it consumes usage and may start a session; it is not a scheduled polling mode. Session auto-start remains a separately enabled feature.

Record endpoint choice, date, CLI version, account type, redacted observations and the intentional departure from upstream in the parity matrix. Live account tests remain pending until performed through an authenticated app; updating this plan does not authorise a generating test now.

### Secrets, refresh ownership and persistence

Replace Credential Manager chunking with **one versioned DPAPI `CurrentUser`-encrypted secret file per profile**. Store it under `%LOCALAPPDATA%\ClaudeUsageTracker`, with an owner-restricted ACL. Serialize the whole new bundle, encrypt it, write and flush an encrypted temporary file in the same directory, then atomically replace the destination. App-created secret backups use the same protection. Verify read-back before exposing a credential change as complete. [DPAPI / ProtectedData](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata?view=net-10.0)

This removes the multi-entry partial-write problem; it does **not** make server-side token rotation and local persistence one transaction. Serialize app-owned refreshes, durably save the returned bundle before publishing it, and stop refreshing if persistence fails. Retain the new bundle in memory for a persistence retry; do not re-submit or restore a known rotated token. A crash before durable persistence may still require sign-in, which must be reported honestly.

Track credential ownership explicitly as **CLI-linked, app-owned or unresolved**, separately from which profile is selected. Inventory the default config directory, configured overrides, linked directories and app-created launcher directories; do not claim to discover every arbitrary folder on disk. While any known CLI credential store holds that account's tokens, keep its stored app copy CLI-linked. Reconcile account identity and token lineage before refresh, linking and switching; ambiguous identity or inaccessible stores make ownership unresolved and prevent automatic rotation. Never log tokens or token fingerprints.

After a verified account switch moves the old account out of the shared CLI files, transfer its latest saved credentials to app-owned only if no other registered CLI store still holds that account, no potentially relevant CLI process is live and no store is unresolved. Conversely, handing app-owned tokens to any CLI store immediately returns them to CLI-linked ownership; do not run an app-owned refresh concurrently with handoff. Use **one app-wide asynchronous lock** around every credential mutation, including refresh, import, deletion, handoff, switch and takeover. Hold it through the refresh request and persistence; ordinary usage reads need not take it. Refreshes are infrequent, so no per-account lock registry is needed. Account identity and token lineage still determine ownership and write-back destinations, not lock selection. External CLI writers do not honour this lock, so retain process/file conflict checks. External copies outside the known inventory cannot be proven absent; show the ownership assumption and treat user-reported copies as linked rather than refreshing blindly.

Port upstream's **idle Claude Code refresh takeover**, subject to the Windows safeguards below, so linked profiles need not go stale merely because no CLI is open overnight. Read and mirror a fresh CLI token without rotating it. For an expired token, require that all relevant known CLI stores are readable and stable, no current-user Claude process/session could be using them, and ownership/lineage is unambiguous. Expiry alone is not proof of idle state: sleep, network failures or a stalled process can leave a live CLI with expired credentials. Refresh once under the app-wide credential lock, durably save the new encrypted bundle, then re-check process/file state and atomically merge/write it back to all stores holding that same lineage, preserving unrelated fields and verifying read-back. This is the same guarded path used before applying an expired account during profile switching. Stores with an independent lineage for the same account are not overwritten.

If a process starts, a store changes or write-back fails during takeover, retain the new encrypted bundle as pending reconciliation, stop further rotation and report the conflict; never replace a newer CLI login or reuse the old refresh token. Multiple stores and remote token rotation are not one transaction, so repair or sign-in may still be needed. If an open/uncertain Claude session prevents takeover, retain labelled stale usage and show **"Waiting for Claude Code to refresh its login"**, not an authentication error. A session left open overnight will commonly take this path; when Claude refreshes on use, re-read its new tokens on the next poll. Distinguish genuinely rejected/revoked credentials from this deferred-refresh state. Record these stricter process/conflict guards as a deliberate Windows adaptation to upstream issue #268. Codex shared-store takeover is not implied by Claude's policy: retain read-through/deferred refresh for CLI-owned Codex tokens until a separate provider-specific takeover is verified, and record that difference explicitly. App-owned Codex credentials may refresh through their normal provider path.

Browser cookies also exist in WebView2's isolated user-data folders, managed by its browser storage. This is an explicit exception to the app-owned secret-file representation; do not export cookies into settings, logs or helper scripts. Clear browser state on disconnect/profile deletion after its browser processes exit.

Keep non-secret settings, per-profile history and the statusline cache separate from secrets, using versioned JSON and atomic writes. Preserve upstream history sampling, retention, chart ranges and CSV/JSON export. Report corrupted storage instead of resetting profiles silently. DPAPI-protected app files are not portable across Windows users/machines; moving a release folder does not migrate its logins.

### Windows tray, notifications and visual design

Use a small owned `Shell_NotifyIcon` wrapper and a known callback HWND, rather than reflecting into WinForms `NotifyIcon`. For unsigned Debug/Release/personal/portable builds, derive each GUID deterministically from a product namespace, the normalised absolute executable path and the logical icon slot (stable profile ID plus metric, not display name). Keep the identity stable for same-path upgrades; never reuse that GUID from another unsigned executable path. On Windows 11 26200 such reuse is not rejected as documented: Explorer re-binds the GUID's entry to the new path (Milestone 1), so a shared GUID would make copies flip one entry rather than fail. Reserve path-independent GUIDs for the signed installer channel in Milestone 7 with consistent publisher signing. Document that moving an unsigned build creates a new tray identity and loses the user's previous visibility preference. [GUID and executable-path restrictions](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-notifyicondataa)

Obtain the icon rectangle through `Shell_NotifyIconGetRect`; convert physical coordinates for per-monitor DPI and clamp the popover to the work area. If no rectangle is available, use the activation position and work area. Test separate checkout/Debug/Release paths, same-path replacement and a moved portable directory. [Tray positioning API](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyicongetrect)

Reproduce the 280-DIP popover, profile header, rows, progress bars, banners and separate sidebar settings window using shared XAML design tokens. Implement themes, keyboard access, accessible names and detachable mode. Use Windows fonts and redistributable icons. Map upstream `zh-ch.lproj` explicitly to .NET `zh-Hans`; do not infer a culture from the upstream folder spelling. Preserve `zh-Hant.lproj` as `zh-Hant` and test both Chinese resource/fallback chains.

Spike tray activation and deactivation as one state machine: clicking an open icon dismisses the popover once, without the deactivation/click sequence reopening it. Handle Explorer restart, overflow icons and multiple monitors. Windows controls overflow placement and icon order; do not offer an ineffective taskbar per-metric ordering setting. Limit tray tooltips to 127 characters and put full details in the popover.

Use Windows App SDK `AppNotificationManager` for notifications in the unpackaged WPF app. Call `Register()` before posting; it establishes click activation without an installer. Marshal callbacks to the UI thread and route clicks to the correct profile. Test cold activation as well as activation of the running single instance. Treat executable-path registration as a relocation risk: test moving the full portable output directory, re-registering from its new location, clicking old/new notifications and cleaning up only the app's stale registrations. Do not assume tray signing rules also solve notification relocation. [Unpackaged .NET notifications](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-dotnet)

Publish both .NET and Windows App SDK dependencies self-contained. Self-contained Windows App SDK 2.5.1 output omits `Microsoft.WindowsAppRuntime.Insights.Resource.dll`, without which `Register()` throws; extract it from the runtime MSIX at build time until the package ships it (Milestone 1). Local `AppNotificationManager` notifications do not require the extra Singleton package; do not add a push-notification runtime dependency. Verify on a clean machine and record registration cleanup, without treating package installation as necessary for local notifications. [Self-contained deployment dependencies](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps)

Map macOS sound names to a documented Windows sound selection, including silent mode; do not redistribute Apple sound files or expose nonfunctional macOS choices.

### CLI files, safe switching and launchers

Implement native file-based CLI linking around `<config dir>/.credentials.json`. File existence is a discovery signal, not proof of a usable login: validate shape, account metadata where available and token expiry, then verify read-only access. Do not port macOS Keychain discovery/migration workarounds.

Separate selecting a profile to view from synchronising the shared CLI account. Account synchronisation can modify both credentials and `oauthAccount` in the resolved `.claude.json`; that file is shared with running Claude sessions. Use `CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS)` and `Process32First`/`Process32Next` to obtain `claude.exe` parent PIDs. Query current-user ownership, executable paths and creation times with limited process-query access. Attribute a child to a profile only if its live parent is a verified app-owned launcher image, the install manifest maps that launcher to the profile/config directory, and the parent's creation time precedes the child's. Include retained launcher images renamed during an upgrade in that manifest. Recheck identities around mutations; never trust a PID alone. [Windows process snapshots](https://learn.microsoft.com/en-us/windows/win32/toolhelp/taking-a-snapshot-and-viewing-processes)

Every other current-user `claude.exe` counts conservatively as using the default/shared config. Inaccessible or ambiguous process information remains unknown and blocks a risky takeover; it cannot prove another linked store idle either. HUD observations can supplement this classification but cannot override an unverified parent chain. Do not read another process's environment, add launcher IPC merely to identify its profile, or infer idle state from an empty HUD. Parent-based attribution is available before the HUD is implemented.

Block shared-account mutation and defer automatic CLI switching while a matching CLI process/session is running or its state is uncertain. Viewing another profile and launching an isolated profile remain possible. Before a permitted switch, take encrypted recoverable backups, re-read and merge only owned fields, detect intervening changes, atomically write and verify both identity and unrelated fields afterward. On conflict stop; do not blindly retry or restore over another writer. Document that uncooperative external writers still leave a residual race and that two CLI files are not a single transaction.

Publish Helper as **NativeAOT** with source-generated JSON serialization. Use direct `.exe` invocation for statusline and launcher entry points. Install `claude-<profile>.exe` aliases under `%USERPROFILE%\.local\bin`, matching upstream's per-user location, with an app-owned alias-to-profile-ID manifest. Resolve the real native `claude.exe` there or on PATH, excluding the helper and every app-owned alias; never recurse into a launcher or overwrite an unrelated file. If the alias directory is absent from PATH, show upstream's warning/instructions instead of editing PATH.

Start native `claude.exe` using `ProcessStartInfo.ArgumentList`, inherited console and the selected `CLAUDE_CONFIG_DIR`. Install the launcher's `Console.CancelKeyPress` handler before starting the child and set `Cancel = true` while waiting, so Ctrl+C reaches the child through the shared console without terminating the waiting parent and returning the shell prompt early. Do not propagate a console-control ignore flag to the child. Await child exit and return its exit code; verify Ctrl+C/Ctrl+Break, repeated interruption and shell behaviour. No `.cmd` trampoline or shell-built argument string; npm-only batch entry points are outside the first native CLI support target.

Generated statusline command paths use forward slashes and quoting appropriate to the selected Git Bash/PowerShell runner. A quoted PowerShell executable path requires invocation syntax; test both runners rather than assuming one command string works in both. Removing an alias does not remove its login directory.

### Stable helper installation, upgrades and repair

Install the integration helper at the fixed per-user path `%LOCALAPPDATA%\ClaudeUsageTracker\bin\ClaudeUsageTracker.Helper.exe`. Hooks and statusline settings reference this installed copy, never an app extraction directory, checkout or Debug/Release output. The launcher copies remain at their fixed `%USERPROFILE%\.local\bin\claude-<profile>.exe` paths, with profile/config mapping stored outside the movable app folder. A portable app therefore has an explicit per-user integration footprint; moving or deleting its folder must not remove the installed helper or launchers.

On an explicit helper install/update, stage and verify the new executable beside the destination. Rename the existing executable to a unique retained filename, then rename the staged copy to the canonical name. Apply the same procedure to each app-owned launcher copy. Existing processes may continue using the retained image while new invocations use the replacement. Do not overwrite an in-use image or terminate a Claude session to release it. Renaming can still fail because of other open handles or protection software; leave the old installation intact and report/defer the update when that happens. [Windows file-move API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)

The two renames are not one transaction: maintain a small install manifest of canonical/staged/retained paths, version and launcher-to-profile mappings so startup can recover an interruption after either rename. If promotion fails, restore the retained canonical name when possible; otherwise show repair-required state. Document a possible brief failed invocation during the rename gap rather than claiming zero downtime. Clean only app-owned retained files once they are no longer in use; defer locked leftovers. Preserve old/new helper protocol compatibility during rollout and do not automatically downgrade a shared installed helper when an older Debug checkout starts.

At app startup and after relocation/upgrade, validate all app-owned hook/statusline executable paths and launcher copies against the install manifest, plus helper existence/version and alias mappings. Show a visible degraded-integration state and offer repair for missing/broken paths, even though async hook failures may be quiet. Repair reinstalls from the current app bundle and changes only app-owned settings entries; never rewrite unrelated commands or silently substitute a different binary. Test repair after an old development output has been cleaned and removal while a launcher session is still alive.

### Fast, secret-free statusline

The helper's statusline mode renders upstream components/colour modes from an atomic **non-secret per-profile cache** and Claude Code stdin. It performs no authentication, credential reads or network requests. A separately gated hook-forwarding mode may use local named-pipe IPC only. Record the statusline design as a deliberate improvement over upstream's cookie-bearing fetch script.

Use a matching cache while its age is at most twice the configured polling interval. Otherwise use available `rate_limits.five_hour` and `rate_limits.seven_day` fields from stdin for that invocation. Missing fields are unavailable, not zero. Do not attach an active profile's cached account limits to a session from another configuration directory, or write unverified stdin data into another profile's history. A stale cache can supply labelled stale data only when identity matches and no stdin value is available. [Claude Code statusline contract](https://code.claude.com/docs/en/statusline)

Measure the NativeAOT helper both directly and through each actual shell runner. Target warm end-to-end p95 below 100 ms and first-run latency below 300 ms on the development machine; report shell overhead separately. Test rapid replacement/cancellation. The documentation confirms cancellation of an in-flight invocation, but does not establish a stable 300 ms debounce guarantee; treat that timing as version-dependent and measure the installed CLI. Do not make correctness depend on it.

### Passive hooks and activity HUD: measure before selecting transport

Preserve exactly the eight baseline events: SessionStart, SessionEnd, UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, Stop and Notification. The user measured roughly two seconds to refuse a .NET connection to a closed local port; this is evidence of risk, not a measured Claude Code delay. The Milestone 1 benchmark uses actual model-driven tool calls and **consumes usage**, potentially starting a session. It requires the user's explicit go-ahead for that run; approving this plan or ordinary implementation does not authorise it. Disclose the chosen cheap available model and trial count before requesting approval.

Run `claude -p` from a disposable scratch folder outside the repository with `--model`, an explicit `--settings <test-file>` and an empty `--setting-sources` value so user/project/local settings do not load. Pass these as actual arguments, preserving the empty argument. The installed CLI's help confirms both settings flags. Use a separate test file per condition; never edit the user's real hook settings. Verify effective hooks before spending usage, including managed/plugin sources that those switches may not suppress. If policy or foreign hooks remain active, report that isolation is incomplete and stop the benchmark rather than disable managed controls. Do not use `--bare`, which would skip the hooks being measured.

Measure at least 20 tool calls in each of four conditions: no hooks, accepting HTTP listener, stopped/crashed listener and restarting listener (**at least 80 calls**, plus any separately approved async comparison). Limit tools/prompts to harmless operations in the scratch folder, keep the model/workload constant and report complete PreToolUse/PostToolUse pair overhead separately from model/network latency. Cap the approved trial count and do not retry extra paid runs silently. Verify settings reload on the tested CLI version. While approval is pending, continue independent work and leave this gate unverified; no production hooks are installed by the benchmark.

**Decision gate:** if stopped-listener HTTP adds 100 ms or more at p95 per tool-call pair over the no-hook baseline, reject it as the default. Prefer direct-exec async command hooks plus named pipes if they pass the same latency test and the installed CLI supports the required fields for all eight events. If HTTP meets the budget in running, stopped and restart cases, retain it to avoid per-event processes. If neither passes, leave HUD integration uninstalled with a documented blocker; do not silently install a synchronous command fallback. Record the selected transport and minimum tested CLI version. Current docs support `args` for no-shell execution, `async` for command hooks, and normal automatic reload of settings-file edits; test those behaviours rather than assuming a universal session-restart requirement. [Claude Code hook contract](https://code.claude.com/docs/en/hooks)

**Preferred alternative when HTTP fails the gate:** install `type: "command"`, an absolute helper `.exe` path, a separate `args` array and `async: true`. No shell or `.cmd` is involved. The NativeAOT helper stamps receipt time, reads a bounded input and forwards only the event/session/tool identifiers and minimal HUD state over a local current-user-restricted named pipe. Do not forward prompts, full tool inputs/results, credentials or transcripts. Use a per-user pipe name, current-user ACL/remote-client rejection, bounded framing/concurrency and an overall helper deadline; connection attempts use a short bounded timeout with no retries when the tracker is down. Missing server/disconnect is an expected dropped observation: exit quietly without output, decisions, context injection or `asyncRewake`. Unexpected failures remain visible through safe diagnostics; do not rely on the CLI enforcing an async timeout.

Measure per-event process/CPU cost and bursts as well as foreground latency. Async forwarding can lose events during CLI teardown or helper cancellation. Helper receipt timestamps support best-effort ordering but do not reveal original emission order when processes start out of order. Correlate session/tool-use IDs, deduplicate lifecycle transitions, never let a late PreToolUse reopen an already-completed tool, and do not revive an ended session without corroborated new-session activity. Test completion-before-start, duplicates, delayed Stop/SessionEnd, missing events and process exit. Retain process checks for refresh safety; an eventually consistent HUD is not an authoritative liveness registry. Upstream HTTP framing/server tests are not production regressions for the pipe choice: mark them inapplicable and replace them with pipe ACL, framing, deadline, offline, burst and ordering tests, while retaining transport-independent event/HUD cases.

**If HTTP is retained:** bind an exclusive `TcpListener` only to `127.0.0.1`, with a random per-user persistent port selected outside the machine's current TCP dynamic and excluded/reserved ranges. Query actual ranges, do not hard-code defaults or use port zero. Local inspection found dynamic ports 1024-15000 plus excluded ranges, including 50000-50059; other machines differ. Attempt an exclusive bind, retry another eligible candidate on collision, persist only a successful selection and revalidate on subsequent launches. Never alter machine port reservations. Use a random 256-bit path secret, owner-restricted config, early authorisation, bounded parser/queues/deadlines and immediate `200 {}` before event processing. Port the upstream HTTP parser/tests only for this route. Loopback itself is not a user-isolation boundary. When the tracker is closed, another user's process could bind the port and receive full hook payloads. This is accepted because multi-user PCs are out of scope (section 1).

For retained HTTP, start the listener before installing owned hooks and remove owned hooks before stopping it on a clean exit. Use conflict-aware read/merge/write with foreign hooks preserved. A crash still leaves hooks behind: startup/shutdown cleanup alone cannot waive the stopped-listener latency gate. For either transport, test live reload after install/remove/endpoint repair and verify the next event uses the new configuration; request restart only when the tested session fails to reload. Async hooks can remain installed while the tracker is closed. Render a floating WPF pill, never emit permission decisions or send input, and document transport/lifecycle differences from upstream.

Milestone 1 result: HTTP passes the gate on CLI 2.1.286. With a local fake Messages endpoint (no usage), the stopped listener cost +2.5 ms p95 and the running and restart cases were similar. An approved real-model run on the stopped listener (Haiku, 40 tool calls) measured +14.7 ms p95. **HTTP is the selected transport.** User-settings edits reload after about one second; `--settings` files do not.

**Accepted decision (2026-10-01): HTTP hooks for all eight baseline events, in upstream's configuration** (`matcher: ""`, `type: http`, tokened URL, `timeout: 3`).
- Claude Code 2.1.286 skips HTTP hooks for SessionStart, so that entry is installed but inert. A session appears in the HUD at its first delivered event, normally UserPromptSubmit, which is how upstream behaves on the same CLI. If a later CLI delivers HTTP SessionStart, the entry works unchanged.
- SessionEnd is delivered, so closed sessions leave the HUD promptly.
- Rejected: a mixed configuration with one async command hook for SessionStart. Its only gain is showing idle sessions sooner, at the cost of a second hook format to install, repair and remove.
- Rejected: async command hooks with a named pipe for all eight. These lost SessionEnd in every run and cost a process per event plus 95-150 ms at every CLI exit. Their data-isolation advantage matters only on multi-user PCs, which are out of scope.
- Re-measure the gate whenever the minimum supported CLI version changes. See [the Milestone 1 log](docs/milestone-1.md#6-hook-transport-latency-and-reload).

### Diagnostics and build location

Include the network log view, but record allowlisted metadata only: operation name, method, sanitised route, status, timing, transport and error category. Never persist raw request/response bodies, prompts, headers, cookies, tokens or hook secret paths. Add fixture-based redaction tests and a clear-log action; export contains only the same safe fields.

Keep build outputs outside Dropbox and outside the app's data root `%LOCALAPPDATA%\ClaudeUsageTracker`, so removing user data never deletes build output and cleaning builds never happens beside secrets. `Directory.Build.props` sets `ArtifactsPath` to `%LOCALAPPDATA%\ClaudeUsageTracker.Build\<checkout-id>` for restore/build/test/publish, with project/configuration separation; it must be set there, not in a `.targets` file, because the SDK reads it early. `<checkout-id>` is the first 16 hex characters of MSBuild's SHA-256 `StableStringHash` of the lower-cased repository path. The same setting applies to CLI and IDE builds. Microsoft.Testing.Platform resolves its default `TestResults` folder against the working directory, so the props file also passes an absolute `--results-directory` under the artifacts root. Visual Studio's `.vs` folder cannot be relocated: git-ignore it and mark it ignored by Dropbox with `Set-Content -Path .vs -Stream com.dropbox.ignored -Value 1`. `.gitignore` alone does not stop Dropbox syncing; verify that restore/build/test create no generated folders in the repository. [Artifacts output layout](https://learn.microsoft.com/en-us/dotnet/core/sdk/artifacts-output)

## 4. Verification matrix and completion rules

- **Regression:** map all 16 upstream suites; preserve applicable behaviours while replacing macOS-only tests and marking HTTP parser/server tests inapplicable if pipes win. Test missing/legacy limits, exact colour/pace thresholds, DST/reset boundaries, history retention, provider capabilities and `zh-ch` to `zh-Hans`/`zh-Hant` resource selection.
- **Authentication:** repeated browser replay versus in-browser fetch, renewal/restart, two isolated profiles, challenge/HTML versus authentication failures, Console independently, read-only OAuth live availability and no silent `/v1/messages` fallback.
- **Secrets:** realistic large synthetic bundles, DPAPI wrong-user failure, interruption before/after atomic replacement, write denial, rotation persistence failure and no retry of known rotated tokens. Local atomicity is not claimed to cover a remote refresh transaction.
- **Concurrency:** the app-wide credential lock serialises refresh/import/deletion/switch/takeover across profiles; external writers still trigger conflicts. Test account/lineage ownership, fresh-token read-through, idle takeover, waiting-for-CLI state while sessions remain open, parent executable/creation-time validation and PID reuse, process start or token change during rotation, partial write-back repair, handoff, remaining alias stores, late requests and preserved foreign fields. No process-environment inference.
- **Hooks:** explicit usage approval, scratch-folder `claude -p` with isolated `--settings`/`--setting-sources`, no foreign hooks or edits, approved model/trial cap, real latency and live reload. If async: direct exec/args without shell, per-event CPU/bursts, pipe ACL/remote rejection, framing/size/deadline bounds, missing server, teardown cancellation and out-of-order/duplicate/missing events. If HTTP: framing/parser bounds, token redaction, dynamic/excluded-range selection, collisions, start/exit edits and crash leftovers. Both: foreign-entry preservation and no permission/context output.
- **Helper:** direct NativeAOT and actual shell timings, stdin rate-limit omissions, cache freshness/identity mismatch, rapid cancellation, quoting/metacharacters, alias recursion/collision protection, missing PATH warning and native child exit/Ctrl+C/Ctrl+Break without early parent exit. Statusline never accesses network/credentials; hook forwarding uses local IPC only.
- **Windows/UI:** light/dark, 100/150/200% and mixed DPI, overflow/anchor fallback, toggle debounce, 127-character tooltips, unsigned path-derived/signed-installer identities, moved executable and visibility-preference reset, Explorer restart, keyboard/accessibility, Chinese mappings and long translations, notification registration/re-registration and old/new cold activation after relocation, sleep/resume and remote desktop.
- **Delivery:** no SDK required by published artifacts; external build output; fixed installed helper/alias paths survive app relocation and build cleanup; concurrent execution during rename-aside upgrade; interruption/promotion/rollback failures; retained-image cleanup and parent attribution; startup detection/repair of missing owned paths; protocol compatibility without silent downgrade. Manual upgrade/registration cleanup precedes signed public install/update/uninstall and rollback.

A milestone is complete only when its required tests and evidence are recorded. Mocked HTTP and screenshots do not establish live authentication or Mac runtime parity. Unavailable account types, missing Mac hardware and unresolved spikes must remain visible in the parity matrix; a failed route must not become a fake success or silently dropped requirement.
